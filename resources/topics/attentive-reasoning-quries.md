# Attentive Reasoning Queries (ARQ)

## 1. 개요 및 배경

LLM이 복잡한 작업을 수행하거나 긴 대화를 이어가다 보면, 초기에 설정된 중요한 지침을 점차 잊어버리거나 추론의 방향이 흐트러지는 현상이 나타난다. Chain-of-Thought(CoT) 프롬프팅이 이 문제를 어느 정도 해결하지만, 자유 형식의 CoT는 추론 과정이 지나치거나 검증이 어려운 방향으로 흘러가는 한계가 있다. 모델이 "단계별로 생각"하더라도 그 단계가 실제로 올바른 방향을 향하고 있는지, 중요한 제약 조건을 놓치지 않는지를 보장하기 어렵다.

**Attentive Reasoning Queries(ARQ)** 는 이 문제를 해결하기 위해 고안된 구조화된 추론 제어 기법이다. ARQ는 자유 형식의 CoT 대신 JSON 스키마 내에 인코딩된 특정 도메인 질문을 통해 모델의 추론 과정을 단계별로 제어하는 구조화된 접근법이다. 이 기법은 긴 대화나 복잡한 Agentic 시나리오 도중 모델이 잊기 쉬운 중요한 지침을 다시 상기시키고, 추론 단계를 세분화하여 최종 결정이 검증 가능하도록 도우며, 특히 할루시네이션 방지와 지침 준수에 탁월한 효과를 발휘한다.

ARQ의 핵심 아이디어는 간단하다. 모델에게 "자유롭게 생각하시오"라고 요청하는 대신, 반드시 답해야 하는 구체적인 질문들을 JSON 구조로 제시하여 추론의 경로를 설계자가 의도한 방향으로 유도한다. 마치 체크리스트처럼 작동하는 이 질문들은 모델이 중요한 판단 기준을 빠뜨리지 않도록 하고, 각 단계의 답변이 다음 단계의 입력으로 이어지면서 최종 결론에 도달하는 구조를 만든다.

이 기법은 특히 LLM을 자율적으로 작동하는 에이전트로 활용하거나, 높은 정확성과 지침 준수가 요구되는 실무 환경에서 점점 더 중요한 역할을 하고 있다.

> **핵심 정의**
> 
> Attentive Reasoning Queries(ARQ)란, 자유 형식의 추론 대신 JSON 스키마로 구조화된 도메인 특화 질문 시퀀스를 통해 LLM의 추론 과정을 단계별로 제어하고, 각 단계의 응답이 검증 가능한 형태로 출력되도록 유도하는 프롬프트 설계 전략이다.
> 
> **핵심 공식:** ARQ = 구조화된 질문 시퀀스+ JSON Schema Encoding + 단계별 검증
> 
> 예시: _"아래 JSON 스키마의 각 질문에 순서대로 답하면서 추론하고, 모든 필드를 채운 후 최종 결론을 도출하시오."_

## 2. 이론적 배경

### 자유 형식 CoT의 한계와 ARQ의 등장

Chain-of-Thought Prompting은 모델이 중간 추론 단계를 거치도록 유도하여 복잡한 문제에서의 정확성을 높이는 데 효과적이다. 그러나 자유 형식의 CoT는 몇 가지 구조적 한계를 가진다.

첫째, **지나친 추론 문제**다. 모델이 단계별로 생각하도록 유도해도, 어떤 단계를 거쳐야 하는지에 대한 제약이 없으면 추론이 작업과 관련 없는 방향으로 흘러가거나 중요한 판단 기준을 건너뛰는 경우가 생긴다. 둘째, **검증의 어려움**이다. 자유 형식의 추론 과정은 사람이 검토하거나 프로그래밍 방식으로 파싱하기 어렵다. 추론이 올바른 방향을 따랐는지 확인하려면 전체 텍스트를 읽어야 한다. 셋째, **지침 제외 문제**다. 긴 대화나 복잡한 Agentic 시나리오에서 모델은 초기에 설정된 중요한 제약 조건이나 지침을 점차 잊어버리는 경향이 있다.

ARQ는 이 세 가지 한계를 JSON 스키마 기반의 구조화된 질문으로 동시에 해결한다. 질문의 순서가 추론의 경로를 정의하고, JSON 형식이 검증을 가능하게 하며, 각 단계의 질문이 중요한 지침을 명시적으로 상기시키는 역할을 한다.

### JSON 스키마가 추론을 구조화하는 원리

JSON 스키마는 데이터의 구조, 타입, 필수 필드를 정의하는 표준 형식이다. ARQ에서 JSON 스키마는 단순한 출력 형식 지정을 넘어, 모델이 반드시 거쳐야 하는 추론 단계를 정의하는 역할을 한다.

각 JSON 필드는 하나의 추론 질문에 대응한다. 모델은 JSON의 모든 필드를 순서대로 채우면서 각 단계의 추론을 수행하고, 이전 필드의 답변이 다음 필드의 추론 기반이 된다. 이 구조는 몇 가지 중요한 특성을 만들어낸다.

첫째, **강제적 순서 준수**다. JSON 필드의 순서가 추론의 순서를 강제하기 때문에, 모델이 중요한 단계를 건너뛰거나 결론을 먼저 내린 후 논거를 끼워 맞추는 방식을 방지할 수 있다. 둘째, **파싱 가능한 검증**이다. 출력이 JSON 형식이기 때문에 각 추론 단계의 결과를 프로그래밍 방식으로 추출하고 검증할 수 있다. **명시적 지침 인코딩**이다. 중요한 제약 조건이나 판단 기준을 필드 이름이나 필드 설명에 직접 인코딩함으로써, 모델이 추론하는 과정에서 이를 지속적으로 참조하게 만든다.

### 에이전틱 시나리오에서의 중요성

ARQ는 특히 LLM이 여러 단계의 행동을 자율적으로 계획하고 실행하는 에이전틱 시나리오에서 그 가치가 두드러진다. 에이전트는 사용자의 초기 지시를 받고 여러 도구를 사용하면서 복잡한 작업을 완료하는데, 이 과정에서 초기 제약 조건을 잊거나 잘못된 방향으로 추론이 누적되면 최종 결과가 의도와 크게 벗어날 수 있다.

ARQ는 각 행동 단계마다 "이 행동이 초기 지침에 부합하는가?", "이전 단계의 결과가 예상과 일치하는가?", "다음 단계로 진행하기 전에 확인해야 할 조건은 무엇인가?"처럼 체크포인트 역할을 하는 질문을 JSON 스키마로 정의함으로써, 에이전트의 행동이 전체 목표로부터 벗어나지 않도록 지속적으로 조정한다.

### 할루시네이션 방지 메커니즘

ARQ가 할루시네이션을 방지하는 원리는 두 가지다. 첫째, 근거 요구(Evidence Requirement)다. JSON 스키마의 각 필드에 "근거", "출처", "확인된 사실"처럼 근거를 명시적으로 요구하는 필드를 포함하면, 모델은 단순히 그럴듯한 내용을 생성하는 대신 실제 근거를 참조하도록 유도된다. 둘째, **단계별 일관성 검증**이다. 각 추론 단계의 결과가 JSON 형식으로 명시되기 때문에, 후속 단계에서 이전 단계의 결과를 참조할 때 불일치가 발생하면 이를 감지하고 수정하는 기회가 생긴다. 일관성 없는 추론이 누적되어 잘못된 결론으로 이어지는 것을 방지하는 구조다.

## 3. 주요 유형 및 적용 방식

ARQ는 어떤 목적으로 추론을 구조화하는가에 따라 여러 유형으로 분류된다.

### 선형 질문 시퀀스 방식

가장 기본적인 형태로, 추론 단계를 선형적으로 나열한 JSON 스키마를 제공하는 방식이다. 각 필드가 하나의 추론 단계에 대응하며, 순서대로 답변하면서 최종 결론에 도달한다. 단순하고 명확한 인과 관계를 따르는 분석이나 판단 작업에 적합하다.

> **선형 ARQ 스키마 예시 — 콘텐츠 품질 검토**
> 
> \`\`\`json
> {
>   "step_1_topic_clarity": "이 콘텐츠의 핵심 주제가 첫 단락에서 명확히 드러나는가? (예/아니오 + 근거)",
>   "step_2_audience_fit": "타깃 독자의 수준에 맞는 어휘와 설명 방식을 사용하고 있는가?",
>   "step_3_logical_flow": "단락 간 논리적 연결이 자연스러운가? 흐름이 끊기는 지점이 있다면 명시하시오.",
>   "step_4_factual_check": "확인이 필요한 수치나 주장이 있는가? 있다면 열거하시오.",
>   "step_5_conclusion": "위 검토를 종합한 최종 품질 평가와 우선 개선 사항 2가지를 제시하시오."
> }
> \`\`\`

### 조건 분기 질문 방식

추론 과정에서 특정 조건에 따라 다음 단계가 달라지는 분기 구조를 JSON 스키마로 표현하는 방식이다. 복잡한 의사결정 트리를 구조화하거나, 다양한 상황에 따라 다른 판단 기준을 적용해야 할 때 활용된다.

각 분기 조건을 JSON 필드로 명시하고, 조건에 따라 참조해야 하는 다음 필드를 지정함으로써 모델이 상황에 맞는 추론 경로를 선택하게 한다. 이는 단순한 선형 추론으로는 처리하기 어려운 복잡한 판단 작업에서 특히 유용하다.

> **조건 분기 ARQ 스키마 예시 — 응답 유형 결정**
> 
> \`\`\`json
> {
>   "query_type_check": "사용자 질문이 사실 확인, 의견 요청, 작업 수행 중 어느 유형인가?",
>   "if_factual": {
>     "evidence_available": "학습 데이터 내 관련 사실이 있는가?",
>     "confidence_level": "확신도를 high/medium/low로 평가하시오.",
>     "response_strategy": "확신도에 따른 응답 방식을 결정하시오."
>   },
>   "if_opinion": {
>     "multiple_perspectives": "고려해야 할 주요 관점 2~3가지를 나열하시오.",
>     "bias_check": "특정 관점에 편향될 위험이 있는가?"
>   },
>   "final_response_plan": "위 분석을 바탕으로 최종 응답 계획을 수립하시오."
> }
> \`\`\`

### 체크포인트 검증 방식

에이전틱 시나리오에서 각 행동 단계마다 초기 지침 준수 여부를 점검하는 체크포인트를 JSON 스키마로 정의하는 방식이다. 행동을 실행하기 전과 후에 반드시 답해야 하는 검증 질문을 포함하여, 에이전트가 의도된 범위를 벗어나지 않도록 지속적으로 조정한다.

이 방식은 특히 외부 도구를 사용하거나 돌이키기 어려운 행동(파일 수정, API 호출, 데이터 변경 등)을 수행하는 에이전트에서 안전장치로 활용된다.

> **체크포인트 ARQ 스키마 예시 — 에이전트 행동 검증**
> 
> \`\`\`json
> {
>   "pre_action_check": {
>     "goal_alignment": "이 행동이 초기 목표와 일치하는가?",
>     "constraint_compliance": "설정된 제약 조건(범위, 권한, 안전 규칙)을 위반하지 않는가?",
>     "reversibility": "이 행동은 취소 가능한가? 취소 불가능하다면 추가 확인이 필요한가?"
>   },
>   "action_execution": "위 체크포인트를 통과했다면 행동을 실행하시오. 통과하지 못했다면 이유를 설명하고 중단하시오.",
>   "post_action_check": {
>     "expected_outcome": "예상 결과와 실제 결과가 일치하는가?",
>     "next_step_validity": "다음 단계로 진행하기 위한 조건이 충족되었는가?"
>   }
> }
> \`\`\`

### 할루시네이션 방지 특화 방식

모델이 사실 확인이 필요한 정보를 생성할 때, 각 주장에 대한 근거와 확신도를 명시적으로 요구하는 JSON 스키마를 적용하는 방식이다. 모델이 그럴듯한 내용을 생성하는 대신 실제 근거를 참조하도록 강제하고, 불확실한 정보에는 명시적으로 불확실성을 표시하게 한다.

> **할루시네이션 방지 ARQ 스키마 예시**
> 
> \`\`\`json
> {
>   "claim_identification": "응답에 포함될 주요 주장이나 사실을 나열하시오.",
>   "evidence_check": "각 주장에 대해 학습 데이터 내 근거가 있는가? 근거가 없거나 불확실하면 명시하시오.",
>   "confidence_assessment": "각 주장의 확신도를 high/medium/low로 평가하시오.",
>   "uncertainty_flagging": "확신도가 low인 항목에 대해 '확인이 필요합니다' 레이블을 붙이시오.",
>   "final_response": "위 검증을 거친 내용만을 포함하여 최종 응답을 작성하시오."
> }
> \`\`\`

## 4. 도메인별 적용 사례

### AI 에이전트 및 자율 작업 시스템

ARQ가 가장 강력하게 활용되는 분야다. 여러 도구를 사용하며 복잡한 작업을 자율적으로 수행하는 에이전트에서, ARQ는 각 행동 단계마다 목표 정렬 여부를 점검하고 중요한 제약 조건을 상기시키는 안전장치 역할을 한다.

코드 작성 에이전트에서는 "요구사항 분석 → 설계 검토 → 구현 → 테스트 계획 → 예외 처리 확인" 순서로 각 단계를 JSON 필드로 정의하고, 모든 단계를 순서대로 거친 후에만 최종 코드를 출력하도록 한다. 데이터 분석 에이전트에서는 "분석 목표 확인 → 데이터 범위 검토 → 방법론 선택 근거 → 결과 해석 → 한계 명시" 순서로 추론을 구조화하여, 분석 과정의 투명성을 높이고 편향된 해석을 방지한다.

> **시스템 프롬프트 예시 — 코드 리뷰 에이전트**
> 
> "당신은 코드 리뷰를 수행하는 AI 에이전트입니다. 모든 리뷰는 아래 JSON 스키마를 완전히 채운 후에만 최종 의견을 출력하시오.
> 
> \`\`\``json
> {
>   "functionality_check": "코드가 요구사항을 충족하는가? 누락된 기능이 있는가?",
>   "security_scan": "보안 취약점(인젝션, 인증 오류, 민감 정보 노출 등)이 있는가?",
>   "performance_review": "명백한 성능 문제(불필요한 루프, 비효율적 쿼리 등)가 있는가?",
>   "readability_assessment": "변수명, 함수명, 주석이 의도를 명확히 전달하는가?",
>   "test_coverage": "엣지 케이스와 예외 처리가 적절히 다루어지고 있는가?",
>   "final_verdict": "위 5개 항목의 검토 결과를 종합한 최종 리뷰 의견과 우선순위별 개선 사항을 제시하시오."
> }
> \`\`\`"
> \`\`\``

### 콘텐츠 생성 및 품질 관리

콘텐츠 생성 분야에서 ARQ는 품질 기준을 JSON 스키마로 정의하여, 모델이 생성 과정에서 각 기준을 순서대로 검토하면서 콘텐츠를 작성하도록 유도한다. 사후 검수가 아닌 생성 과정 자체에 품질 체크포인트를 내재화하는 방식이다.

마케팅 콘텐츠 생성에서는 "타깃 독자 확인 → 핵심 메시지 정의 → 증거/근거 확인 → 브랜드 톤 검토 → 행동 유도 문구 포함 여부 확인" 순서로 ARQ를 적용한다. 기술 문서 작성에서는 "독자 수준 파악 → 필수 포함 정보 목록 → 전문 용어 사용 기준 → 예시 포함 여부 → 다음 단계 안내 포함" 순서로 문서 완성도를 체계적으로 확보한다.

### LLM 기반 챗봇의 지침 준수 강화

고객 응대, 기술 지원처럼 명확한 응답 지침이 있는 챗봇 서비스에서, ARQ는 모델이 긴 대화 중에도 핵심 지침을 망각하지 않도록 각 응답 생성 전에 지침 준수 여부를 체크하는 내부 추론 구조로 활용된다.

중요한 점은 이 내부 추론 과정을 사용자에게 노출하지 않는 것이다. ARQ의 JSON 스키마를 내부 추론 단계로만 활용하고, 최종 필드에만 사용자에게 보여줄 응답을 작성하게 하면, 지침 준수는 강화하면서 사용자 경험은 자연스럽게 유지할 수 있다.

> **내부 추론 ARQ 예시 — 고객 지원 챗봇**
> 
> \`\`\`json
> {
>   "intent_classification": "사용자 질문의 의도를 파악하시오. (정보 요청 / 불만 접수 / 기능 문의 / 기타)",
>   "scope_check": "이 질문이 서비스 지원 범위 내에 있는가? 범위 밖이라면 어떻게 안내해야 하는가?",
>   "policy_compliance": "답변이 서비스 정책(환불 규정, 개인정보 처리 방침 등)을 위반하지 않는가?",
>   "empathy_required": "사용자가 불만이나 어려움을 표현하고 있는가? 공감 표현이 필요한가?",
>   "response_draft": "위 분석을 바탕으로 정책을 준수하는 최종 응답을 작성하시오."
> }
> \`\`\`

### 코드 생성 및 디버깅

코드 관련 작업에서 ARQ는 코드 생성 전 요구사항을 체계적으로 분석하고, 각 설계 결정의 근거를 명시하게 함으로써 코드의 품질과 요구사항 적합성을 높인다. 특히 복잡한 시스템에서 잘못된 가정이나 요구사항 오해로 인한 오류를 사전에 방지하는 데 효과적이다.

디버깅 시나리오에서는 "오류 메시지 분석 → 발생 조건 특정 → 가능한 원인 목록화 → 각 원인의 가능성 평가 → 최우선 검토 원인 선택 → 수정 방안 제시" 순서로 ARQ를 적용하여 체계적인 문제 해결 과정을 구조화한다.

## 5. 다른 프롬프트 기법과의 결합

ARQ는 다른 프롬프트 기법의 약점을 보완하고 강점을 극대화하는 방식으로 결합될 때 가장 강력한 효과를 발휘한다.

### 5-1. ARQ + Chain-of-Thought

자유 형식의 CoT가 가진문제를 ARQ의 구조화된 질문으로 제어하는 결합이다. CoT의 단계별 추론 능력은 유지하면서, 그 추론이 반드시 거쳐야 하는 경로를 JSON 스키마로 정의한다.

자유 형식 CoT에서 모델이 임의로 선택한 추론 단계를 밟는 것과 달리, ARQ + CoT에서는 설계자가 의도한 추론 경로를 따라야 한다. 각 JSON 필드 안에서 자유롭게 추론하되, 어떤 질문에 답해야 하는지는 스키마가 결정한다. 이는 창의성과 구조의 균형을 맞추는 방식이다.

> **결합 프롬프트 예시**
> 
> "아래 JSON 스키마의 각 필드에 단계별 추론 과정을 포함하여 답하시오. 각 필드 내에서는 자유롭게 생각하되, 필드의 순서는 반드시 지켜야 한다.
> 
> \`\`\``json
> {
>   "problem_decomposition": "문제를 구성하는 핵심 요소들을 분해하고 각각의 관계를 설명하시오.",
>   "assumption_check": "풀이 과정에서 전제하는 가정들을 명시하고 타당성을 검토하시오.",
>   "solution_path": "각 단계의 추론 과정을 상세히 서술하면서 풀이를 전개하시오.",
>   "verification": "도출된 답이 문제의 조건을 모두 만족하는지 검증하시오.",
>   "final_answer": "최종 답변을 명확하게 제시하시오."
> }
> \`\`\`"
> \`\`\``

### 5-2. ARQ + Negative Prompting

ARQ의 각 추론 단계에서 피해야 할 패턴을 명시적으로 금지하는 방식이다. 추론의 경로를 구조화하면서 동시에 각 단계에서 발생할 수 있는 오류 패턴을 방지하는 이중 제어가 가능하다.

특히 할루시네이션 방지에서 이 결합이 효과적이다. ARQ가 근거를 요구하는 필드를 정의하고, Negative Prompting이 근거 없는 주장을 금지함으로써, 두 방향에서 동시에 허위 정보 생성을 억제한다.

> **결합 프롬프트 예시**
> 
> "아래 JSON 스키마를 채우면서 분석하시오. 단, 각 필드에서 확인되지 않은 사실을 단정적으로 서술하지 마시오. 불확실한 내용은 반드시 '확인 필요'로 표시하시오.
> 
> \`\`\``json
> {
>   "verified_facts": "확실히 알려진 사실만 나열하시오.",
>   "uncertain_areas": "불확실하거나 추가 확인이 필요한 영역을 명시하시오.",
>   "analysis": "확인된 사실만을 근거로 분석하시오. 추측은 추측임을 명시하시오.",
>   "conclusion": "확실한 결론과 잠정적 결론을 구분하여 제시하시오."
> }
> \`\`\`"
> \`\`\``

### 5-3. ARQ + Role-Based Prompting

특정 전문가 역할의 관점에서 ARQ의 각 질문에 답하도록 유도하는 방식이다. 역할이 추론의 프레임과 우선순위를 설정하고, ARQ가 그 프레임 안에서 반드시 거쳐야 하는 추론 단계를 구조화한다.

예를 들어 "당신은 시니어 보안 엔지니어입니다"라는 역할 지시와 함께, 보안 관점에서 순서대로 검토해야 할 항목들을 ARQ 스키마로 정의하면, 해당 역할의 전문가가 실제로 수행하는 체계적인 검토 과정을 LLM이 재현하게 된다.

### 5-4. ARQ + Verbalized Sampling

ARQ의 각 추론 단계에서 여러 후보 답변을 생성하고 점수를 평가하게 하는 방식이다. 단일 추론 경로가 아니라 각 단계에서 여러 가능성을 탐색한 후 최적의 방향을 선택하면서 다음 단계로 나아가는 구조다.

이 결합은 복잡한 의사결정에서 각 단계마다 최선의 선택을 보장하는 방식으로 활용된다. Tree of Thoughts와 유사하지만, 탐색 구조가 JSON 스키마로 명시적으로 정의된다는 점에서 더 예측 가능하고 검증하기 쉽다.

## 6. 장점과 한계

### 장점

ARQ의 가장 핵심적인 강점은 **추론의 예측 가능성과 검증 가능성**이다. 자유 형식의 추론은 모델이 어떤 경로를 따를지 예측하기 어렵고, 결과가 올바른 과정을 거쳐 도출되었는지 확인하기 어렵다. ARQ는 추론 경로 자체를 JSON 스키마로 정의하기 때문에, 설계자가 의도한 단계가 실제로 수행되었는지를 구조적으로 검증할 수 있다.

**할루시네이션 방지 효과**도 중요한 강점이다. 근거를 명시적으로 요구하는 필드, 확신도 평가 필드, 불확실성 표시 필드를 스키마에 포함함으로써, 모델이 그럴듯한 내용을 생성하는 대신 실제 근거를 참조하도록 구조적으로 유도한다. 이는 단순한 부정 지시보다 훨씬 강력한 할루시네이션 억제 효과를 낸다.

**긴 컨텍스트에서의 지침 유지**도 ARQ의 핵심 가치다. 에이전틱 시나리오나 긴 대화에서 모델이 초기 지침을 망각하는 문제를 각 단계의 체크포인트 질문이 지속적으로 중요 지침을 상기시키는 방식으로 해결한다. 지침을 일회성 지시가 아니라 추론 구조 안에 내재화하는 접근이다.

**파이프라인 자동화 친화성**도 실무적으로 중요한 장점이다. 출력이 JSON 형식이기 때문에 프로그래밍 방식으로 각 추론 단계의 결과를 파싱하고 활용할 수 있다. 특정 단계에서 조건을 만족하지 못하면 자동으로 재시도하거나 다른 경로를 선택하는 자동화 로직을 구현하기 용이하다.

### 한계 및 주의사항

**스키마 설계 비용**이 가장 큰 실무적 한계다. ARQ의 효과는 JSON 스키마의 설계 품질에 직접적으로 의존한다. 어떤 질문을 어떤 순서로 포함할 것인지, 각 필드가 실제로 올바른 추론을 유도하는지를 도메인 전문가가 신중하게 설계해야 한다. 잘못 설계된 스키마는 오히려 추론을 왜곡하거나 중요한 단계를 누락할 수 있다.

**토큰 비용 증가**도 중요한 한계다. ARQ는 모든 추론 단계를 JSON 형식으로 출력하기 때문에 자유 형식 CoT보다 토큰 소비가 많다. 특히 체크포인트 검증 방식처럼 각 행동마다 ARQ를 적용하는 에이전틱 시나리오에서 비용이 급증할 수 있다. 비용 효율을 고려하여 ARQ가 실제로 필요한 중요한 단계에만 선택적으로 적용하는 것이 바람직하다.

**모델의 스키마 준수 한계**도 고려해야 할 점이다. ARQ는 모델이 JSON 스키마를 정확히 따를 것을 전제하지만, 모델이 스키마의 일부 필드를 생략하거나 잘못된 형식으로 응답하는 경우가 발생할 수 있다. 특히 스키마가 복잡하거나 필드 수가 많을수록 준수율이 낮아지는 경향이 있다. 스키마를 간결하게 유지하고, 필드 수를 적정 수준(5~7개)으로 제한하는 것이 권장된다.

**유연성 제약**도 주의해야 할 한계다. 추론 경로를 엄격하게 정의하면 예측 가능성은 높아지지만, 모델이 스키마에 정의되지 않은 중요한 관점을 자유롭게 탐색하는 능력이 제한될 수 있다. 모든 작업에 ARQ를 적용하기보다, 구조화된 추론이 실제로 필요한 작업을 선별하여 적용하는 것이 중요하다.

## 7. 모범 작성 가이드라인

### 도메인 전문성 반영 원칙 — 스키마에 해당 분야의 판단 기준을 인코딩하라

ARQ 스키마의 품질은 해당 도메인에서 실제로 중요한 판단 기준이 얼마나 잘 반영되어 있는가에 달려 있다. 범용적인 질문보다 해당 작업에서 전문가가 실제로 검토하는 항목들을 스키마에 직접 인코딩해야 한다.

예를 들어 코드 보안 검토 스키마에는 인젝션, 인증 오류, 민감 정보 노출처럼 실제 보안 전문가가 점검하는 항목을 포함해야 한다. 콘텐츠 품질 검토 스키마에는 해당 콘텐츠 유형의 업계 기준이 반영되어야 한다. 도메인 전문가와 협력하여 스키마를 설계하거나, 해당 분야의 체크리스트나 평가 기준을 참조하는 것이 효과적이다.

### 순서 설계 원칙 — 인과 관계를 따르는 논리적 순서를 구성하라

ARQ 스키마의 필드 순서는 단순한 나열이 아니라 추론의 인과 관계를 반영해야 한다. 이전 필드의 답변이 다음 필드의 추론 기반이 되는 구조를 설계해야 한다.

일반적으로 효과적인 순서는 "전제 확인 → 제약 조건 점검 → 핵심 분석 → 대안 검토 → 최종 결론" 형태다. 결론을 먼저 내리고 논거를 끼워 맞추는 역방향 추론이 발생하지 않도록, 결론 필드는 항상 마지막에 위치시켜야 한다.

### 간결성 원칙 — 핵심 필드만 포함하고 5~7개를 넘지 마라

스키마가 복잡할수록 모델의 준수율이 낮아지고 토큰 비용이 증가한다. 스키마는 가능한 한 간결하게 유지하되, 반드시 거쳐야 하는 핵심 추론 단계만을 포함해야 한다.

5~7개의 필드가 실용적인 균형점이다. 필드 수가 이를 초과하면 스키마를 분할하거나, 관련 있는 여러 질문을 하나의 필드로 통합하는 방식을 고려한다. 필드 이름은 명확하고 직관적으로 작성하여 모델이 각 필드의 목적을 즉시 이해할 수 있게 해야 한다.

### 내부 추론 분리 원칙 — 사용자에게 보여줄 내용과 내부 추론을 구분하라

ARQ의 추론 과정 전체를 사용자에게 노출할 필요는 없다. 특히 챗봇처럼 사용자 경험이 중요한 서비스에서는 ARQ를 내부 추론 구조로만 활용하고, 마지막 필드에만 사용자에게 보여줄 최종 응답을 작성하게 하는 것이 효과적이다.

"이 JSON의 내용은 내부 추론 과정으로만 사용하시오. 사용자에게는 final_response 필드의 내용만 출력하시오"처럼 명시적으로 구분하면, 지침 준수는 강화하면서 사용자에게는 자연스러운 응답을 제공하는 이중 구조를 구현할 수 있다.

### 반복 검증 원칙 — 스키마를 실제 출력으로 검증하고 개선하라

ARQ 스키마는 한 번에 완성되지 않는다. 초기 스키마를 적용한 후 실제 출력을 검토하여, 모델이 특정 필드에서 일관성 없는 답변을 하거나 중요한 판단을 놓치는 패턴을 파악하고 스키마를 개선하는 반복 과정이 필요하다.

특히 다음 사항을 중점적으로 검토해야 한다. 모델이 자주 생략하는 필드가 있다면 필드 설명을 더 명확히 하거나 필수 여부를 강조한다. 특정 필드의 답변이 너무 짧거나 피상적이면 더 구체적인 질문으로 수정한다. 최종 결론이 중간 추론 과정과 일관성이 없는 경우 필드 간 연결 구조를 재설계한다.

---

Attentive Reasoning Queries(ARQ)는 자유 형식 추론의 한계를 JSON 스키마 기반의 구조화된 질문으로 극복하는 정교한 프롬프팅 기법이다. 추론 경로를 명시적으로 설계함으로써 할루시네이션을 방지하고, 긴 대화나 복잡한 에이전틱 시나리오에서 중요한 지침을 망각하지 않도록 하며, 각 추론 단계의 결과를 검증 가능한 형태로 출력한다.

특히 LLM을 자율 에이전트로 활용하거나 높은 정확성과 지침 준수가 요구되는 실무 환경에서 ARQ의 가치는 더욱 두드러진다. 단순한 프롬프트 수준의 지시가 아니라 추론 구조 자체를 설계하는 접근이기 때문에, 모델의 행동을 보다 예측 가능하고 신뢰할 수 있는 방향으로 제어할 수 있다.

다만 스키마 설계 비용, 토큰 소비 증가, 유연성 제약이라는 한계를 인식하고, 구조화된 추론이 실제로 필요한 고위험·고복잡도 작업에 선택적으로 적용하는 것이 중요하다. Chain-of-Thought, Role-Based Prompting, Negative Prompting과 결합하면 ARQ의 구조적 강점과 각 기법의 고유한 능력이 시너지를 이루어, 더 정교하고 신뢰할 수 있는 LLM 활용이 가능해진다.
