# Negative Prompting Usecase

---

## 개요

Negative Prompting은 LLM에게 하지 말아야 할 것을 명시적으로 지시하여 출력 품질을 제어하는 기법이다. 본 문서는 실제 Eureka Flow에서 Negative Prompting을 적용한 유즈케이스를 기록한다.

긍정 지시만으로 설계된 프롬프트는 모델이 원치 않는 방향으로 흘러가는 것을 막지 못하는 경우가 많다. "마크다운 Header를 사용하세요"라는 긍정 지시보다 "숫자 리스트를 사용하지 마세요"처럼 구체적인 부정 지시를 사용하는 것이 모델을 의도한 방향으로 제어하는 데 더 효과적이다.

---

## 실행 환경

- **모델:** gemini-3-flash-preview

---

## 문제점

모델은 별도의 지시가 없으면 사용자가 원하지 않는 형식과 문구를 자동으로 삽입한다.

**기본 실행 결과**

```
제공해주신 참고문서에 따르면, Eureka Codes의 **Eureka Flow**에서 지원하는 AI 모델은 다음과 같습니다.

**1. Gemini 시리즈**
* gemini-2.5-flash
* gemini-2.5-pro
* gemini-3-flash-preview
* gemini-3.1-pro-preview

**2. GPT 시리즈**
* gpt-5-mini
* gpt-5.1
* gpt-5.2

Eureka Flow는 최신 Gemini 및 GPT 시리즈의 차세대 모델들을 폭넓게 지원하고 있는 것으로 확인됩니다.
```

**문제점 정리**

첫째, 사용자 쿼리를 그대로 반복(Echoing)한다. "제공해주신 참고문서에 따르면, Eureka Codes의 **Eureka Flow**에서 지원하는 AI 모델은 다음과 같습니다"처럼 사용자가 이미 알고 있는 내용을 앞에 붙인다. 이는 불필요한 토큰 낭비이자 가독성을 해치는 패턴이다.

둘째, 숫자 리스트처럼 요청하지 않은 형식이 자동으로 적용될 수 있다.

셋째, 불필요한 마무리 문구를 삽입한다. "확인됩니다", "폭넓게 지원하고 있는 것으로 확인됩니다"처럼 응답을 마무리하는 문구가 자동으로 생성된다. 파이프라인 자동화나 구조화된 출력이 필요한 경우 이런 문구는 방해 요소가 된다.


---

## 유즈케이스

### 주제

Eureka Codes의 Eureka Flow 지원 AI 모델 안내

### 유형

형식 제어 (Format Control)

### 목표

불필요한 반복 제거 + 원하는 형식으로 출력 제어

핵심은 동일한 인풋에서 시스템 프롬프트만 다르게 적용하여 출력 형식이 어떻게 달라지는지 확인하는 것이다. Positive 지시만 추가했을 때와 Negative Prompting을 적용했을 때의 차이를 3단계로 비교한다.

---

## 공통 인풋

기본 실행, Positive 프롬프트 적용, Negative 프롬프트 적용 모두 동일한 유저 인풋을 사용한다.

**User**

```
Eureka Codes의 Eureka Flow에서 지원하는 AI 모델 알려주세요.

참고문서:
- 지원 모델
    - gemini-2.5-flash
    - gemini-2.5-pro
    - gemini-3-flash-preview
    - gemini-3.1-pro-preview
    - gpt-5-mini
    - gpt-5.1
    - gpt-5.2
```

## 3단계 비교

### 1단계 — 기본 실행

별도의 지시 없이 기본 시스템 프롬프트만 적용한 경우다.

**System**

```
당신은 유능한 어시스턴트입니다.
```

**결과**

```
제공해주신 참고문서에 따르면, Eureka Codes의 **Eureka Flow**에서 지원하는 AI 모델은 다음과 같습니다.

**1. Gemini 시리즈**
* gemini-2.5-flash
* gemini-2.5-pro
* gemini-3-flash-preview
* gemini-3.1-pro-preview

**2. GPT 시리즈**
* gpt-5-mini
* gpt-5.1
* gpt-5.2

Eureka Flow는 최신 Gemini 및 GPT 시리즈의 차세대 모델들을 폭넓게 지원하고 있는 것으로 확인됩니다.
```

---

### 2단계 — 긍정 지시 적용

원하는 형식을 긍정 지시로만 추가한 경우다. Header 형식을 지정했지만 불필요한 서론, 마무리 문구, 임의의 설명이 오히려 늘어났다.

**System**

```
당신은 유능한 어시스턴트입니다.
- 마크다운 Header를 사용하세요.
```

**결과**

```
제공해주신 참고 문서를 바탕으로 **Eureka Codes의 Eureka Flow**에서 지원하는 AI 모델 목록을 안내해 드립니다.

# Eureka Flow 지원 AI 모델 목록

Eureka Flow는 최신 성능을 갖춘 Gemini 시리즈와 GPT 시리즈의 다양한 모델을 지원하고 있습니다.

## 1. Gemini 시리즈
Google의 차세대 모델인 Gemini 시리즈 중 다음 모델들을 사용할 수 있습니다.
*   **gemini-2.5-flash**
*   **gemini-2.5-pro**
*   **gemini-3-flash-preview**
*   **gemini-3.1-pro-preview**

## 2. GPT 시리즈
OpenAI의 최신 기술이 반영된 GPT 시리즈 중 다음 모델들을 지원합니다.
*   **gpt-5-mini**
*   **gpt-5.1**
*   **gpt-5.2**

---
사용자는 작업의 목적과 요구되는 성능에 따라 위 모델 중 최적의 모델을 선택하여 Eureka Flow를 활용할 수 있습니다.
```

**문제점**

Header 지시를 추가했는데 숫자 리스트는 그대로 유지되었고, Header가 추가되었다. 긍정 지시는 원하는 형식을 추가할 수 있지만, 원하지 않는 패턴을 제거하긴 어렵다.

---

### 3단계 — Negative Prompting 적용

부정 지시를 추가하여 원하지 않는 패턴을 직접 제거한 경우다.

**System**

```
당신은 유능한 어시스턴트입니다.
- 사용자의 쿼리를 그대로 반복(Echoing)하지 마세요.
- 숫자 리스트 형식을 사용하지 마세요. 마크다운 Header를 사용하세요.
```

**결과**

```
### Gemini 시리즈
* gemini-2.5-flash
* gemini-2.5-pro
* gemini-3-flash-preview
* gemini-3.1-pro-preview

### GPT 시리즈
* gpt-5-mini
* gpt-5.1
* gpt-5.2
```

숫자 없는 Header와 모델 목록만 깔끔하게 출력되었다. 1단계, 2단계와 달리 임의로 추가된 설명이 없다.

## 프롬프트 문장별 전후 비교

| 프롬프트                           | 역할        | 긍정만 적용                        | Negative 적용              |
| ------------------------------ | --------- | ----------------------------- | ------------------------ |
| 사용자의 쿼리를 그대로 반복(Echoing)하지 마세요 | 서론/마무리 제거 | "제공해주신 참고문서를 바탕으로..." 포함      | 서론/마무리 없이 바로 본론          |
| 숫자 리스트 형식을 사용하지 마세요            | 형식 제어     | ## 1. Google Gemini 시리즈 숫자 포함 | 숫자 없이 ### Gemini 시리즈로 출력 |
| 마크다운 Header를 사용하세요             | 형식 유지 강제  | Header 적용되었으나 불필요한 설명 추가      | 깔끔한 Header만 적용           |

## 핵심 결과

이 유즈케이스에서 확인할 수 있는 핵심은 두 가지다.

첫째, 긍정 지시만으로는 출력 형식을 완전히 제어하기 어렵다. "마크다운 Header를 사용하세요"라고만 하면 Header는 생기지만 불필요한 내용은 유지되는 그대로 역효과가 나타났다.

둘째, 부정 지시는 독립적으로 검증 가능하다. "제공해주신"이라는 문구가 있는지 없는지, 숫자 리스트가 있는지 없는지는 결과물을 보면 즉시 확인할 수 있다. 이는 긍정 지시보다 훨씬 명확한 기준이 된다.

```
긍정 지시: "마크다운 Header를 사용하세요"
→ Header는 생겼지만
  불필요한 내용은 유지됨

부정 지시: "숫자 리스트 사용하지 마세요"
          "Echoing하지 마세요"
→ 원하지 않는 패턴이 제거됨
→ 결과가 예측 가능해짐
```

---

긍정 지시로 해결되지 않던 것이 부정 제약 하나로 바로 제거되었다. Negative Prompting은 구체적인 패턴을 직접 명시할수록 효과적이다.
