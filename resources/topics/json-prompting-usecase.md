# JSON Prompting Usecase

---

## 개요

JSON Prompting은 프롬프트에 JSON 스키마를 명시적으로 정의하여 LLM이 자연어 서술 대신 구조화된 JSON 객체를 출력하도록 유도하는 기법이다. 본 문서는 실제 Eureka Flow에서 JSON Prompting을 적용한 유즈케이스를 기록한다.

LLM은 기본적으로 자연어로 응답하도록 설계되어 있다. 별도의 스키마 정의 없이는 형식이 제각각이고 파싱이 불가능한 출력이 나온다. JSON 스키마와 Output Contract를 함께 적용하면 즉시 파이프라인에서 활용 가능한 구조화된 데이터를 얻을 수 있다.

---

## 실행 환경

- **모델:** gemini-3-flash-preview

---

## 문제점

별도의 스키마 정의 없이 작업을 요청하면 모델이 형식, 분량, 구조를 스스로 판단한다. 자연어로 출력되어 파싱이 불가능하고 매번 다른 형식으로 결과가 나온다.

---

## 유즈케이스

### 주제

블로그 콘텐츠 아웃라인 자동 생성

### 유형

Flat 스키마 + Output Contract

### 목표

자연어 출력과 JSON 스키마 적용 출력을 비교하여 JSON Prompting의 효과를 확인한다.
동일한 인풋에서 시스템 프롬프트만 다르게 적용하여 출력이 어떻게 달라지는지 보여준다.

---

## 공통 인풋

1단계와 2단계 모두 동일한 유저 인풋을 사용한다.

**User**

```
Negative Prompting 키워드로 블로그 콘텐츠 아웃라인 구조를 정리해줘.

참고 문서:

Negative Prompting은 LLM에게 하지 말아야 할 것을
명시적으로 지시하여 출력 품질을 제어하는 기법이다.
긍정 지시만으로는 모델이 원치 않는 방향으로
흘러가는 것을 막지 못하는 경우가 많다.
구체적인 부정 제약을 사용하는 것이
모델을 의도한 방향으로 제어하는 데 더 효과적이다.

유형:
- 내용 기반: 특정 주제나 정보 차단
- 형식 기반: 출력 구조/레이아웃 제어
- 말투/스타일 기반: 특정 어휘나 문체 억제
- 구조적 기반: 추론 방식이나 행동 패턴 제어
```

---

## 2단계 비교

### 1단계 — 기본 실행

별도의 스키마 없이 기본 시스템 프롬프트만 적용한 경우다.

**System**

```
당신은 유능한 어시스턴트입니다.
```

**결과**

```
제공해주신 참고 문서를 바탕으로, 'Negative Prompting(부정 프롬프팅)'을 주제로 한 블로그 콘텐츠 아웃라인을 정리해 드립니다.

## [블로그 아웃라인]
"하지 마세요"라고 말할 때 결과가 바뀐다

### 1. 서론: 왜 내가 원하는 대로 답이 나오지 않을까?
- 긍정적인 지시만으로는 AI의 답변이 산으로 가는 이유
- LLM의 출력 품질을 정교하게 제어하는 개념 소개

### 2. Negative Prompting이란 무엇인가?
...

### 6. 결론
...

#프롬프트엔지니어링 #NegativePrompting #LLM활용법
```

마크다운 헤더, 목차, 해시태그가 자동으로 생성되었다.
6개 섹션에 블로그 작성 팁까지 포함되어 분량이 과도하게 늘어났다. 자연어 출력이라 시스템에서 파싱이 불가능하다.

---

### 2단계 — JSON 스키마 적용

Output Contract와 JSON 스키마를 추가한 경우다.

**System**

```
당신은 유능한 어시스턴트입니다.
- 모든 필드를 반드시 포함하세요.
- JSON 외 어떤 텍스트도 포함하지 마세요.
```

**JSON 스키마**

```json
{
  "type": "OBJECT",
  "properties": {
    "title": {
      "type": "STRING",
      "description": "제목"
    },
    "intro": {
      "type": "ARRAY",
      "items": {
        "type": "STRING"
      },
      "description": "서론. 핵심 포인트 리스트"
    },
    "content": {
      "type": "ARRAY",
      "items": {
        "type": "STRING"
      },
      "description": "본문. 핵심 포인트 리스트"
    },
    "conclusion": {
      "type": "ARRAY",
      "items": {
        "type": "STRING"
      },
      "description": "마무리. 핵심 포인트 리스트"
    }
  },
  "required": [
    "title",
    "intro",
    "content",
    "conclusion"
  ]
}
```

**결과**

```json
{
  "title": "Negative Prompting: LLM의 출력 품질을 극대화하는 부정 지시문의 활용법",
  "intro": [
    "Negative Prompting의 정의와 LLM 출력 제어에서의 역할",
    "긍정 지시문만으로는 해결되지 않는 모델의 편향성 문제",
    "부정 제약을 통한 정밀한 결과물 도출의 중요성"
  ],
  "content": [
    "내용 기반 제어: 특정 주제나 불필요한 정보의 포함을 명시적으로 차단",
    "형식 기반 제어: 출력의 구조와 레이아웃을 원하는 형태로 고정",
    "말투 및 스타일 제어: 특정 단어 사용 금지 및 일관된 문체 유지",
    "구조적 제어: 모델의 추론 과정이나 특정 행동 패턴을 제한하여 정확도 향상"
  ],
  "conclusion": [
    "Negative Prompting은 프롬프트 엔지니어링의 필수적인 도구",
    "긍정적 지시와 부정적 제약의 균형 있는 사용 권장",
    "더욱 정교하고 신뢰할 수 있는 AI 응답 생성을 위한 마무리"
  ]
}
```

스키마를 정확히 준수하여 title, intro, content, conclusion 네 개 필드가 모두 포함되었다. JSON 외 텍스트, 마크다운 헤더, 해시태그가 사라지고 즉시 파싱 가능한 구조화된 데이터가 출력되었다.

## 프롬프트 구성요소별 역할 분석

|구성요소|내용|역할|
|---|---|---|
|Output Contract|JSON 객체만 출력, 마크다운 금지|자연어 출력 방지|
|스키마 정의|title, intro, content, conclusion|출력 구조 강제|
|스키마 배치|유저 프롬프트 마지막|생성 시점에 스키마 참조|
|description|각 필드 설명|모델의 필드 이해 향상|

## 적용 효과

|항목|1단계 (기본 실행)|2단계 (JSON 스키마 적용)|
|---|---|---|
|출력 형식|자연어, 마크다운|구조화된 JSON|
|분량|과도하게 김|필요한 필드만|
|파싱 가능 여부|불가|즉시 가능|
|형식 일관성|매번 다름|스키마로 고정|
|파이프라인 활용|불가|즉시 활용 가능|

---

## 핵심 결과

스키마 없이 요청했을 때 모델은 형식과 분량을 스스로 판단하여 마크다운 헤더, 목차, 해시태그까지 자동으로 생성했다. 사람이 읽기에는 풍부하지만 시스템이 처리하기에는 불가능한 형태였다.

Output Contract와 JSON 스키마를 추가하자 결과가 달라졌다. 스키마를 정확히 준수한 구조화된 데이터가 출력되었고 즉시 파이프라인에서 활용 가능한 형태가 되었다.

> 스키마 없을 때: 모델이 형식을 스스로 판단 → 자연어 출력 → 파싱 불가
> 
> Output Contract + 스키마 적용: 구조 강제 → 즉시 파싱 가능 → 파이프라인 활용

---

## JSON Prompting 원칙

- **Output Contract** — "JSON 객체만 출력하시오"만으로는 부족하다. 마크다운 금지, 모든 필드 포함처럼 구체적인 금지 사항을 함께 명시해야 준수율이 높아진다
- **스키마는 마지막에** — 스키마와 Output Contract는 유저 프롬프트 마지막에 배치한다. 모델이 응답 생성 시점에 스키마를 가장 최근 정보로 참조한다
- **타입 명시** — 각 필드의 타입과 description을 명확히 정의할수록 모델이 올바른 값을 생성할 가능성이 높아진다
