# JSON Prompting

## 1. 개요 및 배경

LLM은 기본적으로 자연어로 응답하도록 설계되어 있다. 이는 사람과의 대화에서는 이상적이지만, LLM을 소프트웨어 시스템의 구성 요소로 통합하려 할 때는 심각한 문제가 된다. 애플리케이션이 LLM의 응답을 파싱하여 다음 처리 단계로 넘기려면, 응답이 예측 가능하고 일관된 구조를 가져야 한다. 자연어 응답은 이 요구를 충족할 수 없다.

**JSON Prompting**은 이 문제를 해결하기 위해 등장한 기법이다. 프롬프트 끝에 명확한 JSON 스키마를 정의하여 모델이 기계 판독이 가능한 구조화된 응답을 반환하도록 강제하는 기술로, LLM을 외부 시스템이나 API에 통합할 때 필수적인 기능이다.

JSON은 키-값 쌍으로 데이터를 표현하는 경량 데이터 교환 형식으로, 사실상 모든 프로그래밍 언어에서 파싱이 가능하다. LLM이 JSON 형식으로 응답하면, 애플리케이션은 응답을 텍스트로 처리하는 대신 구조화된 데이터로 직접 활용할 수 있다. 이는 LLM을 단순한 대화 도구가 아니라 소프트웨어 파이프라인의 핵심 컴포넌트로 활용하는 현대적 AI 시스템 설계의 기반이 된다.

오늘날 LLM 기반 애플리케이션의 대부분은 JSON Prompting을 핵심 인터페이스로 활용한다. 콘텐츠 분류, 감정 분석, 정보 추출, 에이전트 행동 결정처럼 LLM의 판단 결과를 후속 시스템이 활용해야 하는 모든 시나리오에서 JSON Prompting은 필수 기법으로 자리잡았다.

> **핵심 정의**
> 
> JSON Prompting이란, 프롬프트에 JSON 스키마를 명시적으로 정의하여 LLM이 자연어 서술 대신 해당 스키마를 준수하는 구조화된 JSON 객체를 출력하도록 유도하는 프롬프트 설계 전략이다.
> 
> **핵심 공식:** JSON Prompting = 작업 지시 + 스키마 정의(Schema Definition) + 출력  Contract
> 
> 예시: _"아래 제품 리뷰를 분석하고, 오직 JSON만 반환하시오: `{"sentiment": "positive|negative|neutral", "score": 0.0~1.0, "key_topics": []}`"_

## 2. 이론적 배경

### LLM의 자연어 편향과 구조화 출력의 필요성

LLM은 사전 학습 단계에서 자연어 텍스트를 생성하도록 최적화되어 있다. 이 편향은 RLHF 과정을 통해 더욱 강화되는데, 인간 평가자들이 일반적으로 유창하고 설명적인 자연어 응답을 선호하기 때문이다. 결과적으로 LLM은 별도의 지시 없이는 JSON 형식의 응답보다 서술형 응답을 생성하는 경향이 있다.

이 편향을 극복하기 위해 JSON Prompting은 두 가지 전략을 사용한다. 첫째는 **명시적 형식 지시**다. "오직 JSON만 반환하시오"처럼 출력 형식을 직접 지정하여 자연어 서술 충동을 억제한다. 둘째는 **스키마 제시**다. 모델에게 채워야 할 구체적인 데이터 구조를 보여줌으로써, 모델이 해당 구조에 맞게 정보를 추출하고 조직화하도록 유도한다. 이 두 전략의 결합이 JSON Prompting의 핵심 메커니즘이다.

### Output Contract — 출력 계약의 개념

JSON Prompting에서 **Output Contract는 모델이 반드시 준수해야 하는 출력 형식의 약속이다. "오직 JSON만 반환하라(Return ONLY JSON)"는 문구와 함께 스키마를 프롬프트의 마지막에 배치하여 모델의 서술형 응답을 방지한다.

출력 계약의 핵심은 세 가지다. 첫째, **독점성(Exclusivity)**이다. JSON 외의 어떠한 텍스트도 출력에 포함되어서는 안 된다는 것을 명확히 한다. 모델이 JSON 앞뒤에 설명 텍스트를 붙이거나, 마크다운 코드 펜스(\`\`\`json)로 감싸거나, "여기 결과입니다:"처럼 서론을 추가하는 것을 방지한다. 둘째, **완전성(Completeness)**이다. 스키마의 모든 필드가 채워져야 하며, 임의로 필드를 생략할 수 없다는 것을 명시한다. 셋째, **타입 준수(Type Compliance)**다. 각 필드의 데이터 타입(문자열, 숫자, 배열, 불리언 등)을 명시하여 모델이 올바른 타입으로 값을 생성하도록 한다.

### Thought of Structure (ToS) — 구조 사전 추론

**Thought of Structure(ToS)** 는 모델이 JSON을 생성하기 전 데이터 구조에 대해 먼저 추론하도록 하여 복잡한 스키마 준수율을 높이는 기법이다. Chain-of-Thought가 문제 풀이 과정을 먼저 서술하게 하는 것처럼, ToS는 JSON 생성 전에 어떤 데이터를 어떤 구조로 표현할 것인지를 먼저 계획하게 한다.

복잡한 중첩 JSON 스키마나 다수의 필드가 있는 경우, 모델이 즉시 JSON을 생성하려 하면 필드를 빠뜨리거나 잘못된 타입을 사용하는 오류가 발생하기 쉽다. ToS는 이를 방지하기 위해 "JSON을 생성하기 전에 각 필드에 들어갈 내용을 먼저 계획하시오"처럼 사전 추론 단계를 명시적으로 요청한다. 이 계획 단계에서 모델은 입력 데이터를 분석하고 각 필드에 적합한 값을 식별한 후, 그 계획을 바탕으로 정확한 JSON을 생성한다.

### 스키마 정의 방식과 모델의 이해

LLM에게 JSON 스키마를 전달하는 방식은 크게 세 가지로 나뉜다. 첫째, **인라인 예시 방식**이다. 실제 JSON 객체의 예시를 그대로 보여주는 방식으로, 모델이 구조를 직관적으로 이해할 수 있다. 둘째, **필드 설명 방식**이다. 각 필드의 이름, 타입, 의미를 텍스트로 설명하는 방식으로, 복잡한 스키마에서 모델의 이해를 돕는다. 셋째, **JSON Schema 표준 방식**이다. 공식 JSON Schema 형식(`"$schema"`, `"type"`, `"properties"` 등)을 사용하여 스키마를 정의하는 방식으로, 가장 명확하지만 프롬프트 길이가 길어진다. 실무에서는 이 세 가지를 작업의 복잡도에 따라 혼합하여 사용하는 경우가 많다.

## 3. 주요 유형 및 적용 방식

JSON Prompting은 스키마의 복잡도와 적용 목적에 따라 여러 유형으로 분류된다.

### Flat 스키마 방식

중첩 없이 키-값 쌍으로만 구성된 단순한 JSON 스키마를 사용하는 방식이다. 감정 분석, 분류, 간단한 정보 추출처럼 출력이 단순하고 명확한 작업에 적합하다.

스키마가 단순할수록 모델의 준수율이 높고 파싱 오류 가능성이 낮다. 가능하면 단순한 스키마로 시작하고, 필요한 경우에만 복잡도를 높이는 것이 권장된다.

> **Flat 스키마 예시 — 감정 분석**
> 
> \`\`\`
> 아래 텍스트를 분석하고 오직 JSON만 반환하시오. 다른 텍스트는 포함하지 마시오.
> 
> 텍스트: "배송이 예상보다 빨랐고 제품 품질도 만족스럽습니다."
> 
> 반환 형식:
> {
>   "sentiment": "positive | negative | neutral",
>   "confidence": 0.0에서 1.0 사이의 숫자,
>   "primary_emotion": "만족 | 불만 | 중립 | 기쁨 | 실망 중 하나",
>   "summary": "감정의 핵심 이유를 한 문장으로"
> }
> \`\`\`

### 중첩 스키마 방식

객체 안에 객체나 배열이 포함된 중첩 구조의 JSON을 출력하는 방식이다. 복잡한 정보를 계층적으로 표현하거나, 여러 항목을 배열로 추출해야 하는 작업에 활용된다.

중첩 스키마는 표현력이 높지만 모델의 준수율이 낮아지는 경향이 있다. ToS를 함께 적용하거나, 복잡한 스키마를 여러 단계로 분할하여 순차적으로 처리하는 방식이 효과적이다.

> **중첩 스키마 예시 — 제품 리뷰 상세 분석**
> 
> \`\`\`
> 아래 리뷰를 분석하고 오직 JSON만 반환하시오.
> 
> {
>   "overall_sentiment": "positive | negative | neutral",
>   "score": 1에서 5 사이의 정수,
>   "aspects": [
>     {
>       "category": "품질 | 배송 | 가격 | 서비스 중 하나",
>       "sentiment": "positive | negative | neutral",
>       "mention": "해당 측면에 대한 원문 내용"
>     }
>   ],
>   "would_recommend": true 또는 false,
>   "key_improvement": "개선이 필요한 점 한 가지 또는 null"
> }
> \`\`\`

### Output Contract 강화 방식

모델이 JSON 외의 텍스트를 출력하지 않도록 출력 계약을 여러 방식으로 강화하는 방식이다. 단순히 "JSON만 반환하시오"라는 지시 외에도, 구체적으로 금지되는 출력 패턴을 명시하여 준수율을 높인다.

실무에서는 모델이 자주 범하는 위반 패턴을 파악하고 이를 명시적으로 금지하는 방향으로 Output Contract를 지속적으로 개선한다.

> **강화된 Output Contract 예시**
> 
> \`\`\`
> [출력 규칙 — 반드시 준수하시오]
> - JSON 객체만 출력하시오. 그 외 어떤 텍스트도 포함하지 마시오.
> - \`\`\`json 또는 \`\`\` 같은 마크다운 코드 펜스를 사용하지 마시오.
> - "여기 결과입니다:", "분석 결과:" 같은 서론 문구를 붙이지 마시오.
> - 모든 필드를 반드시 포함하시오. 값이 없으면 null을 사용하시오.
> - 문자열 값은 반드시 큰따옴표로 감싸시오.
> - 배열이 비어 있으면 []를 사용하시오. 필드 자체를 생략하지 마시오.
> \`\`\`

### Thought of Structure(ToS) 적용 방식

JSON 생성 전에 데이터 구조를 먼저 계획하는 단계를 명시적으로 포함하는 방식이다. 복잡한 스키마나 정보 추출이 어려운 텍스트에서 준수율을 높이는 데 효과적이다.

ToS 단계에서의 계획 텍스트는 최종 출력에 포함하지 않도록 별도로 지시하거나, 내부 추론 단계로만 활용하도록 설계한다. 사용자에게는 최종 JSON만 전달되어야 하기 때문이다.

> **ToS 적용 프롬프트 예시**
> 
> \`\`\`
> 아래 회의록에서 정보를 추출하시오.
> 
> [단계 1 — 내부 계획 (출력하지 마시오)]
> JSON을 생성하기 전에 다음을 먼저 파악하시오:
> - 참석자 이름과 역할이 몇 명인가?
> - 결정된 사항이 몇 가지인가?
> - 각 액션 아이템의 담당자와 기한은?
> 
> [단계 2 — 오직 아래 JSON 형식만 출력하시오]
> {
>   "meeting_date": "날짜 또는 null",
>   "attendees": [{"name": "이름", "role": "역할"}],
>   "decisions": ["결정 사항 목록"],
>   "action_items": [
>     {"task": "작업", "owner": "담당자", "deadline": "기한 또는 null"}
>   ]
> }
> \`\`\`

## 4. 도메인별 적용 사례

### LLM 기반 AI 파이프라인 및 에이전트

JSON Prompting이 가장 핵심적으로 활용되는 분야다. LLM을 자율 에이전트로 운영하거나, 여러 LLM 호출이 연쇄적으로 이어지는 파이프라인에서 JSON Prompting은 각 단계 간의 데이터 교환 인터페이스 역할을 한다.

에이전트가 다음 행동을 결정할 때는 "사용할 도구(tool), 입력 파라미터(parameters), 예상 결과(expected_output), 실패 시 대안(fallback)"처럼 행동 계획을 JSON으로 출력하게 한다. 이 JSON을 파이프라인이 파싱하여 실제 도구를 호출하고, 결과를 다시 JSON으로 받아 다음 에이전트 호출의 입력으로 넘기는 구조가 현대 AI 시스템의 기본 아키텍처다.

> **에이전트 행동 결정 JSON 스키마 예시**
> 
> \`\`\`json
> {
>   "reasoning": "이 행동을 선택한 이유 한 문장",
>   "action": {
>     "tool": "사용할 도구 이름",
>     "parameters": {"param1": "값1", "param2": "값2"},
>     "expected_output": "예상되는 결과 형태"
>   },
>   "confidence": 0.0에서 1.0 사이,
>   "fallback_action": "실패 시 대안 또는 null"
> }
> \`\`\`

### 콘텐츠 분석 및 분류 자동화

대량의 텍스트 콘텐츠를 자동으로 분류하거나 구조화된 정보를 추출하는 시스템에서 JSON Prompting은 핵심 인터페이스다. 고객 리뷰 분석, 뉴스 기사 분류, 소셜 미디어 모니터링처럼 LLM의 이해 능력을 구조화된 데이터로 변환해야 하는 모든 분석 파이프라인에서 활용된다.

콘텐츠 모더레이션 시스템에서는 "violation_type", "severity", "flagged_content", "recommended_action"처럼 모더레이션 결정에 필요한 모든 정보를 JSON으로 출력하게 하여, 인간 검토자나 자동화 시스템이 즉시 처리할 수 있도록 한다. 감정 분석 파이프라인에서는 전체 감정뿐만 아니라 측면별(제품, 배송, 서비스) 감정을 JSON 배열로 추출하여 세분화된 분석을 가능하게 한다.

### 이미지 생성 AI 프롬프트 구조화

이미지 생성 AI에서 프롬프트를 체계적으로 관리하고 재사용하기 위해, 프롬프트의 구성 요소를 JSON으로 구조화하는 방식이 활용된다. LLM에게 원하는 이미지를 설명하면, 이미지 생성에 최적화된 프롬프트 요소들을 JSON으로 추출하여 이미지 생성 시스템에 전달한다.

"subject", "style", "lighting", "composition", "negative_elements", "quality_modifiers"처럼 이미지 생성의 각 구성 요소를 JSON 필드로 정의하면, 사용자의 자연어 요청을 이미지 생성 시스템이 직접 처리할 수 있는 구조화된 데이터로 변환하는 파이프라인을 구축할 수 있다.

## 5. 다른 프롬프트 기법과의 결합

JSON Prompting은 다른 기법과 결합할 때 각 기법의 강점을 유지하면서 출력을 구조화하는 이중 효과를 낸다.

### JSON Prompting + Chain-of-Thought (ToS)

CoT의 단계별 추론 능력을 JSON 생성에 적용하는 방식이다. 복잡한 스키마에서 즉각적으로 JSON을 생성하려 하면 오류가 발생하기 쉬운데, CoT 방식으로 먼저 각 필드에 들어갈 내용을 계획한 후 JSON을 생성하게 하면 준수율이 크게 향상된다. 이것이 앞서 설명한 Thought of Structure(ToS)의 기본 원리다.

내부 추론 단계는 출력에 포함하지 않고, 최종 JSON만 출력하도록 지시하는 것이 중요하다. "먼저 각 필드에 들어갈 내용을 마음속으로 정리하고, 오직 최종 JSON 객체만 출력하시오"처럼 추론은 내부적으로만 수행하도록 유도한다.

> **결합 프롬프트 예시**
> 
> \`\`\`
> 아래 고객 피드백에서 정보를 추출하시오.
> 
> [내부 추론만 — 출력하지 마시오]
> 1. 언급된 제품이나 서비스 영역은?
> 2. 명확한 감정 표현이 있는가?
> 3. 구체적인 수치나 날짜가 있는가?
> 4. 개선 요청이 있는가?
> 
> [출력] 오직 아래 JSON만 반환하시오:
> {
>   "category": "제품 | 배송 | 서비스 | 가격 | 기타",
>   "sentiment": "positive | negative | neutral | mixed",
>   "urgency": "high | medium | low",
>   "action_required": true 또는 false,
>   "summary": "핵심 내용 한 문장"
> }
> \`\`\`

### JSON Prompting + Negative Prompting

JSON 출력에서 발생하는 일반적인 오류 패턴을 부정 지시로 명시적으로 금지하는 방식이다. 모델이 자주 범하는 JSON 형식 위반을 파악하고 이를 명시적으로 차단함으로써 준수율을 높인다.

실무에서 자주 발생하는 JSON 형식 위반에는 마크다운 코드 펜스 추가, 설명 텍스트 삽입, 스키마에 없는 필드 임의 추가, 숫자 필드에 문자열 반환, 배열 필드에 단일 객체 반환, null 대신 "N/A" 문자열 사용 등이 있다. 이 패턴들을 부정 지시 목록으로 정리하여 프롬프트에 포함하면 준수율이 유의미하게 향상된다.

> **결합 예시 — JSON 위반 패턴 차단**
> 
> \`\`\`
> [절대 하지 마시오]
> - JSON 앞뒤에 설명 텍스트를 추가하지 마시오
> - \`\`\`json 또는 \`\`\` 마크다운 구문을 사용하지 마시오
> - 스키마에 정의되지 않은 필드를 추가하지 마시오
> - 숫자 타입 필드에 문자열을 반환하지 마시오
> - null 대신 "없음", "N/A", "" 빈 문자열을 사용하지 마시오
> - 배열 타입 필드에 단일 객체를 반환하지 마시오
> 
> [오직 아래 JSON만 반환하시오]
> { ... }
> \`\`\`

### JSON Prompting + Role-Based Prompting

특정 전문가 역할의 관점에서 JSON 필드를 채우도록 유도하는 방식이다. 역할이 JSON 각 필드에 담길 내용의 전문적 깊이와 관점을 결정하고, JSON 스키마가 그 출력을 구조화한다.

예를 들어 "당신은 시니어 보안 분석가입니다"라는 역할과 함께 보안 분석 JSON 스키마를 제공하면, 단순히 스키마만 제공했을 때보다 각 필드의 내용이 더 전문적이고 정확하게 채워진다. 역할이 출력의 질을 높이고, JSON 스키마가 출력의 구조를 보장하는 이중 제어 구조다.

### JSON Prompting + ARQ

ARQ의 구조화된 추론 질문을 JSON 스키마로 표현하는 방식이다. ARQ가 추론의 경로를 정의하고, JSON Prompting이 각 추론 단계의 결과를 구조화된 형태로 출력하게 한다. 이 결합은 추론 과정의 투명성과 파이프라인 처리 가능성을 동시에 확보한다.

특히 에이전틱 시스템에서 에이전트의 각 추론 단계를 JSON으로 기록하면, 에이전트의 행동 이력을 데이터베이스에 저장하거나 디버깅에 활용하거나 감사(Audit)에 사용하는 것이 가능해진다.

## 6. 장점과 한계

### 장점

JSON Prompting의 가장 핵심적인 강점은 **시스템 통합 가능성**이다. LLM의 출력이 구조화된 JSON이면 어떤 프로그래밍 언어로 작성된 시스템이든 즉시 파싱하여 활용할 수 있다. 이는 LLM을 독립적인 챗봇이 아니라 소프트웨어 아키텍처의 핵심 컴포넌트로 통합하는 것을 가능하게 한다.

**일관성과 예측 가능성**도 핵심 강점이다. 자연어 응답은 같은 질문에도 매번 다른 형식과 구조로 반환될 수 있지만, JSON 스키마를 정의하면 출력 구조가 일관되게 유지된다. 이는 파이프라인의 안정성을 높이고 예외 처리 로직을 단순화한다.

**자동화 친화성**도 중요한 장점이다. JSON 출력은 코드로 자동 처리하기 용이하기 때문에, LLM의 판단 결과를 사람의 개입 없이 다음 처리 단계로 자동으로 전달하는 완전 자동화 파이프라인을 구현할 수 있다.

**선택적 필드 처리**가 가능하다는 점도 실용적인 장점이다. JSON의 키-값 구조는 특정 필드에만 선택적으로 접근하거나, 여러 JSON 객체에서 동일한 필드를 배치 처리하는 것을 용이하게 한다.

### 한계 및 주의사항

**스키마 준수율의 불완전성**이 가장 근본적인 한계다. LLM은 확률적으로 동작하기 때문에, 명확한 스키마를 제시해도 때로는 형식을 위반하거나 필드를 생략하거나 잘못된 타입을 사용하는 경우가 발생한다. 특히 스키마가 복잡하거나 필드 수가 많을수록 준수율이 낮아진다. 이 때문에 출력 후 검증과 재시도 로직이 필수적이다.

**검증 및 재시도 비용**도 고려해야 한다. JSON 파싱 실패나 스키마 검증 실패 시 재시도가 필요한데, 이는 추가 API 호출 비용과 지연 시간을 발생시킨다. 신뢰성 높은 시스템 설계를 위해 Zod(TypeScript), Pydantic(Python)처럼 스키마 검증 라이브러리를 사용하여 출력을 검증하고 실패 시 자동으로 재시도하는 루프를 구성하는 것이 권장된다.

**복잡한 스키마에서의 정보 손실**도 주의해야 할 한계다. JSON 스키마는 출력 구조를 강제하지만, 동시에 스키마에 정의되지 않은 유용한 정보가 누락되는 경우가 생긴다. 자연어 응답에서는 모델이 자유롭게 추가 관찰이나 주의사항을 포함할 수 있지만, 엄격한 JSON 스키마는 이런 유연성을 제한한다. "additional_notes" 같은 자유 텍스트 필드를 스키마에 포함하면 이 문제를 부분적으로 완화할 수 있다.

**모델 의존성**도 고려해야 한다. JSON 형식 준수 능력은 모델마다 차이가 있다. 대형 모델은 복잡한 스키마도 잘 따르는 반면, 소형 모델에서는 준수율이 크게 낮아질 수 있다. 사용하는 모델의 JSON 출력 능력을 사전에 평가하고, 필요에 따라 스키마 복잡도를 조정하는 것이 필요하다.

## 7. 모범 작성 가이드라인

### Output Contract 설계 원칙 — 금지 사항을 명시적으로 열거하라

"JSON만 반환하시오"라는 단순한 지시만으로는 충분하지 않은 경우가 많다. 실제 서비스에서 모델이 자주 위반하는 패턴을 파악하고, 이를 구체적으로 금지하는 Output Contract를 설계해야 한다.

효과적인 Output Contract는 두 부분으로 구성된다. 첫 번째는 포함해서는 안 되는 것의 목록(마크다운 구문, 설명 텍스트, 추가 필드 등)이고, 두 번째는 반드시 포함해야 하는 것의 기준(모든 필드 포함, 올바른 타입, null 처리 방식 등)이다. 두 방향에서의 명확한 계약이 준수율을 높인다.

### 스키마 단순화 원칙 — 필요한 필드만 포함하고 중첩을 최소화하라

스키마는 작업에 필요한 최소한의 필드만 포함해야 한다. 불필요한 필드가 많을수록 모델이 모든 필드를 올바르게 채울 가능성이 낮아지고, 출력 토큰 수도 증가한다.

중첩 구조는 꼭 필요한 경우에만 사용하고, 3단계 이상의 중첩은 피하는 것이 권장된다. 중첩이 불가피하다면 ToS를 적용하여 모델이 JSON 생성 전에 구조를 먼저 계획하도록 유도한다.

### 타입 명시 원칙 — 각 필드의 타입과 허용 값을 명확히 정의하라

스키마에서 각 필드의 데이터 타입과 허용되는 값의 범위를 명확히 명시해야 한다. "sentiment: positive 또는 negative 또는 neutral"처럼 열거형 값을 명시하거나, "score: 0.0에서 1.0 사이의 소수"처럼 숫자 범위를 지정하면 모델이 올바른 값을 생성할 가능성이 높아진다.

불리언 필드는 `true 또는 false`로, 날짜 필드는 "YYYY-MM-DD 형식 또는 null"처럼 예외 처리 방식까지 명시하는 것이 효과적이다.

### 검증 및 재시도 설계 원칙 — 출력 검증을 시스템 구조에 내재화하라

JSON Prompting을 실무 시스템에 적용할 때, 출력 검증과 재시도 로직은 선택이 아니라 필수다. Zod(TypeScript), Pydantic(Python), Joi(JavaScript)처럼 스키마 검증 라이브러리를 사용하여 모델 출력의 구조적 유효성을 자동으로 검증하고, 검증 실패 시 오류 정보를 포함하여 재시도하는 루프를 구성해야 한다.

재시도 시에는 단순히 동일한 프롬프트를 재전송하는 것이 아니라, 검증 실패 이유를 프롬프트에 포함하여 모델이 오류를 인식하고 수정하도록 유도하는 것이 효과적이다. "이전 응답에서 score 필드가 숫자가 아닌 문자열로 반환되었습니다. score는 반드시 0.0에서 1.0 사이의 숫자여야 합니다. 다시 시도하시오"처럼 구체적인 오류 피드백을 제공한다.

### 스키마 배치 원칙 — 스키마는 프롬프트의 마지막에 위치시켜라

Output Contract와 JSON 스키마는 프롬프트의 마지막 부분에 배치하는 것이 효과적이다. LLM은 컨텍스트의 후반부에 위치한 지시를 생성 시점에 더 강하게 참조하는 경향이 있기 때문이다. 작업 설명, 입력 데이터, 필요한 맥락 정보를 먼저 제공하고, 스키마와 Output Contract를 마지막에 배치하면 모델이 응답을 생성하는 시점에 스키마를 가장 최근에 참조한 정보로 처리하게 된다.

---


JSON Prompting은 LLM을 단순한 대화 도구에서 소프트웨어 시스템의 핵심 컴포넌트로 전환하는 기술적 기반이다. 프롬프트에 JSON 스키마를 정의하고 Output Contract로 출력 형식을 강제함으로써, LLM의 자연어 이해 능력을 기계가 처리할 수 있는 구조화된 데이터로 변환한다. 이는 LLM을 외부 시스템, API, 자동화 파이프라인과 통합하는 모든 시나리오에서 필수적인 기능이다.

Output Contract로 형식을 강제하고, Thought of Structure(ToS)로 복잡한 스키마의 준수율을 높이며, Zod나 Pydantic 같은 검증 라이브러리로 출력을 검증하고 재시도 루프를 구성하는 3단계 접근이 실무에서 신뢰할 수 있는 JSON Prompting 시스템을 구축하는 핵심 전략이다.

스키마 준수율의 불완전성이라는 근본적 한계를 인식하고, 검증과 재시도를 시스템 구조에 내재화하는 설계가 중요하다. Chain-of-Thought, Negative Prompting, Role-Based Prompting, ARQ와 결합하면 JSON 출력의 구조적 정확성과 내용적 품질을 동시에 확보하는 더 강력한 시스템을 구현할 수 있다.
