# ARQ Prompting Usecase

---

## 개요

Attentive Reasoning Queries(ARQ)는 자유 형식의 CoT 대신 JSON 스키마로 구조화된 질문 시퀀스를 통해 LLM의 추론 과정을 단계별로 제어하는 기법이다. 본 문서는 실제 Eureka Flow에서 ARQ를 적용한 유즈케이스를 기록한다.

자유 형식 CoT는 "단계별로 생각하세요"라고 유도하지만 어떤 단계를 거칠지는 모델이 스스로 결정한다. 중요한 항목을 건너뛰거나 근거 없이 주관적으로 평가하는 경우가 생긴다. ARQ는 반드시 답해야 하는 질문을 순서대로 정의하여 설계자가 의도한 추론 경로를 강제한다.

---

## 실행 환경

- **모델:** gemini-3-flash-preview

## 문제점

자유 형식 CoT로 분석을 요청하면 모델이 분석 항목과 순서를 스스로 판단한다. 항목이 매번 달라지고 근거 없이 주관적인 평가가 포함되며 파싱이 불가능한 자연어로 출력된다.

---

## 유즈케이스

### 주제

블로그 글 톤앤스타일 분석

### 유형

선형 질문 시퀀스 (Linear ARQ)

### 목표

자유 형식 CoT와 ARQ 적용을 비교하여 추론 구조 설계의 효과를 확인한다. 동일한 인풋에서 시스템 프롬프트만 다르게 적용하여 출력이 어떻게 달라지는지 2단계로 비교한다.

---

## 공통 인풋

1단계와 2단계 모두 동일한 유저 인풋을 사용한다.

**User**

```
아래 블로그 글의 톤과 스타일을 분석해줘.

제목: 
Negative Prompting: AI 출력을 정밀하게 제어하는 법

내용:
LLM은 기본적으로 친절한 어시스턴트로
동작하도록 훈련되어 있다.
이 특성은 일반 대화에서는 장점이지만,
구조화된 데이터 추출이나 자동화
파이프라인에서는 오히려 노이즈로 작용한다.

"마크다운 Header를 사용하세요"처럼
긍정 지시만 추가하면 원하는 형식은
생기지만, 불필요한 서론과 마무리 문구는
그대로 유지된다.
반면 "숫자 리스트를 사용하지 마세요"처럼
부정 지시를 명시하면 원하지 않는 패턴이
즉시 제거된다.

긍정 지시는 원하는 것을 추가하고
부정 지시는 원하지 않는 것을 제거한다.
두 방향의 제어를 함께 설계할 때
출력이 가장 예측 가능해진다.
```

## 2단계 비교

### 1단계 — 자유 형식 CoT

"단계별로 생각하세요"라고만 지시한 경우다. 어떤 항목을 어떤 순서로 분석할지는 모델이 스스로 결정한다.

**System**

```
당신은 유능한 어시스턴트입니다.
- 답변 전에 단계별로 생각하세요.
```

**결과**

```
제시해주신 블로그 글의 톤과 스타일을 단계별로 분석해 드리겠습니다.

---

### 1. 전체적인 톤 (Tone)

*   **전문적이고 분석적인 (Professional & Analytical):** LLM의 작동 원리(친절한 어시스턴트)를 언급하며 현상을 분석하고, 그에 따른 해결책을 제시하는 전문가적 시각이 담겨 있습니다.
*   **실용적이고 목적 지향적인 (Pragmatic & Goal-oriented):** 감성적인 서술을 배제하고 '정밀한 제어', '예측 가능성' 등 효율성과 결과물의 품질에 집중하는 실무적인 태도를 보입니다.
*   **단호하고 명료한 (Decisive & Clear):** "~작용한다", "~제거된다"와 같은 단정적인 종결 어미를 사용하여 독자에게 신뢰감을 주고 메시지를 명확하게 전달합니다.

### 2. 문체 및 스타일 (Style)

*   **간결한 문장 구조 (Concise Sentences):** 문장이 길지 않고 핵심 위주로 구성되어 있습니다. 불필요한 수식어를 줄여 가독성을 높였습니다.
*   **대조(Contrast)의 활용:** 
    *   '긍정 지시' vs '부정 지시'
    *   '원하는 것 추가' vs '원하지 않는 것 제거'
    *   이러한 대조 구조를 통해 개념의 차이를 선명하게 부각합니다.
*   **논리적 전개 (Logical Flow):** 
    *   [현상/문제점] → [사례 비교] → [결론/원칙] 순서로 전개되어 짧은 글임에도 논리적 완결성이 높습니다.
*   **기술적 어휘 사용 (Technical Vocabulary):** LLM, 파이프라인, 노이즈, 마크다운, 출력 등 IT/AI 분야의 전문 용어를 적재적소에 사용하여 타겟 독자(개발자나 프롬프트 엔지니어링 관심자)에게 적합한 스타일을 유지합니다.
*   **가독성을 고려한 편집:** 줄바꿈을 자주 활용하여 모바일이나 웹 환경에서 한눈에 읽히도록 구성되었습니다.

### 3. 요약 및 타겟팅

*   **스타일 요약:** 불필요한 미사여구 없이 핵심 원리와 실전 팁을 전달하는 **'미니멀리스트 기술 블로그'** 스타일입니다.
*   **예상 독자:** AI를 업무에 활용하려는 직장인, 개발자, 혹은 프롬프트 엔지니어링의 효율성을 높이고 싶은 사용자.

이 글은 정보를 빠르게 습득하고자 하는 현대 독자들의 소비 패턴에 최적화된, **담백하면서도 힘 있는 지식 전달형 스타일**이라고 볼 수 있습니다.
```

분석 항목과 순서를 모델이 스스로 결정했다. 요청하지 않은 타겟팅까지 자동으로 포함되었다. 자연어로 출력되어 파싱이 불가능하고 매번 다른 구조로 출력될 수 있다.

---

### 2단계 — ARQ 적용

분석 항목과 JSON 스키마를 명시적으로 정의한 경우다.

**System**

```
당신은 유능한 어시스턴트입니다.
- 아래 블로그 글의 톤과 스타일을 다음 순서대로 반드시 분석하세요.

[분석]
1. tone: 격식체 수준을 1~5로 평가하고 근거를 한 문장으로 작성하세요.
2. structure: 구조 유형을 분석하세요.(소제목형/번호형/흐름형/혼합형)
3. readability: 독자 접근성을 1~5로 평가하고 근거를 한 문장으로 작성하세요.
4. summary: 위 1~3 분석을 종합한 최종 평가를 두 문장으로 작성하세요.

단, 결론을 먼저 정한 후 분석을 끼워 맞추지 마세요.
각 항목은 반드시 순서대로 분석하며 이전 항목의 결과를 다음 항목에 반영해야합니다.
```

**JSON 스키마**

```json
{
  "type": "OBJECT",
  "properties": {
    "tone": {
      "type": "OBJECT",
      "properties": {
        "score": { "type": "NUMBER" },
        "reason": { "type": "STRING" }
      },
      "required": ["score", "reason"]
    },
    "structure": { "type": "STRING" },
    "readability": {
      "type": "OBJECT",
      "properties": {
        "score": { "type": "NUMBER" },
        "reason": { "type": "STRING" }
      },
      "required": ["score", "reason"]
    },
    "summary": { "type": "STRING" }
  },
  "required": ["tone", "structure", "readability", "summary"]
}
```


**결과**

```json
{
  "tone": {
    "score": 4,
    "reason": "문장 종결 어미로 '~이다', '~한다'를 사용하여 객관적이고 전문적인 정보를 전달하는 격식 있는 어조를 유지하고 있습니다."
  },
  "structure": "흐름형",
  "readability": {
    "score": 5,
    "reason": "문장이 짧고 명확하며, 긍정 지시와 부정 지시의 대비를 통해 핵심 개념을 쉽게 이해할 수 있도록 구성되었습니다."
  },
  "summary": "전문적인 정보를 간결하고 논리적인 흐름으로 전달하여 독자가 핵심 내용을 빠르게 파악할 수 있도록 돕는 글입니다. 명확한 대비 구조와 격식 있는 문체를 통해 기술적 개념에 대한 신뢰도와 가독성을 동시에 확보했습니다."
}
```

정의된 항목만 순서대로 분석되었다. 각 항목마다 수치와 근거가 포함되었고 JSON 형식으로 즉시 파싱 가능한 구조로 출력되었다. 요청하지 않은 내용은 포함되지 않았다.

## 프롬프트 구성요소별 역할 분석

| 구성요소      | 내용                                       | 역할                 |
| --------- | ---------------------------------------- | ------------------ |
| 분석 항목 정의  | tone / structure / readability / summary | 반드시 거쳐야 할 추론 단계 강제 |
| 순서 명시     | 1→2→3→4 순서 지정                            | 추론 경로 제어           |
| 근거 요구     | 점수 + 한 문장 근거                             | 주관적 평가 방지          |
| 역방향 추론 금지 | 결론 먼저 정하지 마시오                            | 할루시네이션 방지          |
| 연결 원칙     | 이전 항목 결과를 다음에 반영                         | 단계별 일관성 확보         |

## 적용 효과

| 항목       | 1단계 (자유 형식 CoT) | 2단계 (ARQ 적용) |
| -------- | --------------- | ------------ |
| 분석 항목    | 모델이 임의 결정       | 정의된 항목만 분석   |
| 분석 순서    | 매번 다름           | 순서 강제        |
| 근거 포함    | 없음              | 항목마다 포함      |
| 출력 형식    | 자연어             | JSON 구조화     |
| 파싱 가능 여부 | 불가              | 즉시 가능        |
| 재현 가능성   | 낮음              | 높음           |

## 핵심 결과

자유 형식 CoT로 분석을 요청했을 때 모델이 항목과 순서를 스스로 결정하여 요청하지 않은 내용까지 자동으로 포함되었다. 자연어로 출력되어 파싱이 불가능하고 매번 다른 구조로 출력될 수 있다.

분석 항목과 순서를 ARQ로 정의하자 결과가 달라졌다. 정의된 항목만 순서대로 분석되었고 각 단계마다 수치와 근거가 포함되었다. JSON 형식으로 즉시 파싱 가능한 구조로 출력되었다.

> 자유 형식 CoT: "단계별로 생각하세요" → 모델이 항목과 순서 임의 결정 → 매번 다른 구조
> 
> ARQ 적용: 설계자가 의도한 추론 경로 강제 → 일관된 구조, 즉시 파싱 가능

## ARQ 원칙

- **분석 항목 정의** — 반드시 거쳐야 할 추론 단계를 명시적으로 정의할수록 누락 항목이 줄어든다
- **순서 강제** — 필드 순서가 추론의 경로를 결정한다. 결론 필드는 항상 마지막에 위치시켜야 한다
- **근거 요구** — 각 단계에서 수치와 근거를 함께 요구하면 주관적 평가와 할루시네이션을 방지할 수 있다
- **역방향 추론 금지** — "결론을 먼저 정한 후 분석을 끼워 맞추지 마시오"를 명시하면 추론 품질이 높아진다
- **CoT와의 차이** — CoT가 "단계별로 생각하라"고 유도한다면 ARQ는 "이 순서대로 생각하라"고 경로를 직접 설계한다
